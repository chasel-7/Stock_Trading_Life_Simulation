后端架构与模块设计方案

我们推荐采用 Approach 1：轻量模块化单体方案

A

Approach 1 (推荐)：模块化 FastAPI 单体 + SQLite

设计：将核心业务逻辑、数据库模型和校验逻辑打包在一个轻量 FastAPI 服务中，使用 SQLAlchemy (或 SQLModel) 操作 SQLite。

结构：
backend/
├── app/
│ ├── models/      # DB 模型 (User, Record, Stock)
│ ├── schemas/     # Pydantic 请求/响应模型
│ ├── services/    # 核心业务 (校验服务, 排行榜服务)
│ ├── api/         # 路由控制器 (v1/auth, v1/game)
│ └── database.py  # 数据库连接与 Session 初始化
└── main.py          # 入口点

B

Approach 2：FastAPI + SQLite + Redis (缓存/排行榜版)

设计：引入 Redis 作为缓存。每日股票历史数据直接从 Redis 读取以加速校验；全服排行榜分数缓存在 Redis Sorted Sets 中，实现秒级高并发排行更新。

特点：读性能极佳，但引入了外部依赖，本地开发和部署相对复杂一些。

为什么推荐 Approach 1？

  • 开发极其迅速：无需配置 Redis 服务，全部依赖均可通过 pip 解决，开发者甚至可以直接通过单条命令启动。
  • SQLite 并发足够：我们主要使用 SQLite 进行“写入战绩”和“拉取排行榜”。对于个人项目和中小型发布，SQLite 的读写性能（每秒几千次写入）绰绰有余。
  • 易于后续集成 Redis：我们的服务层 (Services) 会保持抽象，如果未来并发极高，可以非常平滑地在排行榜模块中引入 Redis。
